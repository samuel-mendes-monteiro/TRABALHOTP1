1. Introdução

O sistema adota o estilo de arquitetura em camadas (layers) com duas camadas. A camada de Apresentação é responsável pela interface com o usuário (cin/cout) e pela validação dos dados de entrada. A camada de Serviço é responsável pela lógica de negócio e pelo armazenamento dos dados em memória. Cada camada é decomposta em módulos: cinco na Apresentação e quatro no Serviço, num total de nove módulos.

Os módulos interagem exclusivamente por meio de serviços especificados em interfaces, declaradas no código como classes abstratas compostas por métodos virtuais puros (pasta include/Interfaces). Isso vale tanto entre as camadas (Apresentação → Serviço) quanto entre os próprios módulos da camada de Serviço. Cada módulo de Serviço guarda seus objetos num contêiner próprio, que nenhum outro módulo acessa.

2. Módulos e interfaces entre as camadas

A figura 1 apresenta os módulos em notação de diagrama de componentes da UML. Cada interface é fornecida (bola) por um módulo da camada de Serviço e requerida (soquete) por um módulo da camada de Apresentação. O módulo Pessoas fornece duas interfaces: IAuthenticationService e IPersonService.

A função main não é um módulo: ela cria os contêineres, os serviços, a sessão e as controladoras, liga cada módulo às interfaces de que ele depende (injeção de dependência) e executa o menu principal, que encaminha a opção escolhida à controladora correspondente.

4. Interações entre os módulos da camada de Serviço

Algumas regras de negócio envolvem mais de uma entidade. Nesses casos, um módulo de Serviço requer a interface fornecida por outro módulo, como mostra a figura 2. Nenhum módulo acessa o contêiner de outro.

  • Projetos → IPersonService: valida se o gestor do projeto existe e tem o papel GESTOR.
  • Pessoas → IProjectService: impede excluir ou trocar o papel de quem é gestor de algum projeto.
  • Cartões de Atividades → IPersonService: valida se o responsável existe e tem o papel DESENVOLVEDOR.
  • Pessoas → ITaskService: impede excluir ou trocar o papel de quem é responsável por algum cartão.
  • Quadros → IProjectService: valida a existência do projeto ao qual o quadro pertence.
  • Cartões de Atividades → IBoardService: valida a existência do quadro e lê o seu limite de WIP.
  • Quadros → ITaskService (WIP e cascata): obtém o WIP atual (o limite não pode ficar abaixo dele) e exclui os cartões de um quadro excluído.
  • Projetos → IBoardService: exclui os quadros de um projeto excluído (e, por consequência, os seus cartões).

Essas dependências garantem as multiplicidades do diagrama de classes e que a exclusão de uma entidade não resulte em inconsistência, conforme exigido pelo enunciado.

6. Classes compartilhadas, controladoras e contêineres

Domínios. As 11 classes de domínio (Email, Identifier, Limit, Name, Password, Priority, Role, Size, State, Text, Timestamp) validam o formato dos dados e são usadas por todos os módulos. A camada de Apresentação usa os domínios para validar a entrada antes de acionar os serviços.

Entidades. As 4 classes de entidade (Person, Project, Board, Task) têm atributos que são instâncias de domínios e são os dados trocados pelas interfaces.

Controladoras. Na camada de Apresentação, as classes *Controller são as controladoras de interação com o usuário. Na camada de Serviço, as classes *Service são as controladoras da lógica de negócio e realizam as interfaces.

Contêineres. As classes PersonContainer, ProjectContainer, BoardContainer e TaskContainer mantêm os objetos em memória. Cada uma pertence a um único módulo da camada de Serviço e só é acessada pelo serviço desse módulo.
